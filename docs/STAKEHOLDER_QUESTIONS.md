# 질문 사다리: 답변이 구현을 바꾸게 만들기

Notion의 문제 정의·운영진 인터뷰·워크북을 바탕으로 구성한 자체 준비법입니다. 실제 배점이나 정답 질문 목록이 아닙니다.

## 3라운드

| 라운드 | 묻는 목적 | 질문 예시 |
| --- | --- | --- |
| 1. 맥락 | 사용자·현재 절차·불편 파악 | 지금 누가 어떤 순서로 검토하며 어디서 실수가 자주 생기나요? |
| 2. 규정과 예외 | 처리 결과를 바꾸는 조건 확인 | 어느 문서가 우선이며, 누락·상충·중복은 누가 판단하나요? |
| 3. 완료 기준 | 최소 범위와 검수 사례 합의 | 필수 출력은 무엇이고 반드시 맞아야 할 정상·경계·예외 사례는 무엇인가요? |

처음부터 어려운 기술 용어로 묻지 않아도 됩니다. README에 명확한 것을 다시 묻거나 담당자에게 구현 순서 전체를 대신 정해 달라고 하지는 않습니다.
위 표의 예시는 열린 질문도 받는 사람 담당자용입니다. 구체 질문에만 답하는 담당자에게는 아래 절처럼 사실 하나·물음표 하나의 질문으로 바꿔 씁니다.

## 8칸 질문 지도

1. 왜 이 일이 필요한가?
2. 누가 언제 결과를 쓰는가?
3. 어떤 입력과 정상 예시가 있는가?
4. 무엇이 승인·반려·보류를 결정하는가?
5. 문서 충돌·정보 누락·실패는 어떻게 다루는가?
6. 결과의 형식·이유·내보내기 중 무엇이 필수인가?
7. 반드시 확인할 대표 사례는 무엇인가?
8. 필수·제외·미정의 정리가 맞는가?

모든 칸을 정해진 개수만큼 묻는 시험이 아닙니다. 이미 주어진 사실은 사용하고, 구현 방향이 바뀌는 질문을 먼저 고릅니다.

## 답변에 따른 후속 질문

| 받은 답변 | 이어서 확인할 것 | 구현에 주는 영향 |
| --- | --- | --- |
| '최대 4명' | 본인을 포함한 수인가, 0명·문자·빈값은? | 숫자 변환과 경계·오류 상태 |
| '최신 문서 우선' | 무엇을 기준으로 최신인가, 시행일과 예외는? | 버전·적용일 선택 |
| '중복은 제외' | 중복 키는 무엇인가, 내용이 다른 중복도 같은가? | 중복 제거와 상충 보류 구분 |
| '이유도 필요' | 행별 이유인가, 요약만인가, 원 식별자는? | 결과 스키마와 추적 가능성 |
| '화면이면 됨' | 어떤 조작이 반드시 가능해야 하는가? | 입력·필터·오류 안내·저장 범위 |
| 답변이 없음 | 해당 불확실성을 보류로 표시해도 되는가? | 임의 승인·반려 대신 미정 유지 |

## 질문에서 구현까지 한 줄로

**질문 → 담당자 답 → 확정 규칙/남은 모호함 → 바뀐 기능 → 기대 사례**

자체 예: '중복이면?' → '같은 ID의 다른 내용은 사람이 검토' → '둘 중 하나를 덮어쓰지 않음' → '상충 상태와 원행 보존' → '같은 ID 두 값의 예상 결과를 먼저 정함'.

질문을 많이 했다는 사실보다 어떤 결정이 바뀌었는지 설명할 수 있는지가 중요합니다.

## 구체 질문에만 답하는 담당자 에이전트

담당자 역할 에이전트(업무·고객·운영 담당)는 질문을 무제한으로 받지만 막연한 질문에는 답하지 않을 수 있습니다. 이때는 질문 수를 아끼는 것보다 엣지 케이스·애매한 표현·문서와 데이터의 차이를 빠짐없이 한 사실씩 묻는 편이 낫습니다. 멘트는 Codex가 한 턴에 몰아서 쓰고, 참가자가 검토해 직접 보냅니다. 공식 규칙이 질문 방식·횟수를 정하면 그 규칙이 우선합니다.

여기서 **질문**은 사실 하나를 묻는 문장(물음표 하나)이고, **메시지**는 담당자 채팅에 한 번 보내는 전송 단위입니다.

- 무제한 여부: 공식 안내로 판단합니다. 안내가 없으면 모호한 질문이 거절되고 질문 수 제한 안내도 없는 것을 관측했을 때 무제한으로 봅니다.
- 무제한이어도 결과·판정·테스트·화면을 바꾸지 않는 질문은 하지 않습니다.
- P0·P1을 먼저 끝냅니다(예: 과제 초반 20~30분 안). P3(표시 문구)는 기본 가정을 원장에 기록하고 남는 시간에만 묻습니다.
- 놓치기 쉬운 범주: 권한(볼 수 있나·없나)만 묻고 역할별 화면·출력 구성 요소(예: 사서 화면에 꼭 있어야 하는 연체 도서 목록·반납 처리)를 빠뜨리기 쉽습니다. 역할마다 따로 묻습니다.

| 구분 | 질문이 제한된 사람 담당자 | 구체 질문에만 답하는 담당자 에이전트 |
| --- | --- | --- |
| 한 번에 묻는 양 | 질문 2~3개, 답을 받은 뒤 재평가 | 첫 메시지에 번호 붙인 질문 2개로 전송 단위 시험. 둘 다 답하면 메시지당 3~5개, 첫 질문만 답하거나 거절하면 메시지당 1개 |
| 묻는 범위 | 설계를 바꾸는 큰 질문 위주 | 용어·단위·경계값·빈값·동점·문서-데이터 차이·역할별 화면 구성까지. 결과를 바꾸지 않는 질문은 제외 |
| 질문 형태 | 열린 질문도 가능 | 예/아니오·수치·선택지로 답할 수 있는 확인형 |
| 답이 모호할 때 | 가정 후 진행 | 쪼개기·선택지·샘플 행·내 가정 확인으로 최대 2회 재질문 후 가정 기록 |
| 사용할 Skill | stakeholder-interview | stakeholder-agent-questioning |

| 모호한 질문 | 구체 질문 (합성 예) |
| --- | --- |
| 대출 한도는 어떻게 처리할까요? | 1인 대출 한도가 5권일 때 정확히 5번째 책 대출은 허용인가요, 거절인가요? |
| 재고가 이상하면 알아서 하면 되나요? | 재고 수량이 음수인 행은 오류로 표시하고 합계에서 빼도 되나요? |
| 연체 기준이 뭔가요? | 반납 예정일 당일에 반납하면 연체 0일로 보면 되나요? |
| 화면은 사용자마다 다른가요? | 회원 화면에서는 다른 회원의 대출 내역을 숨겨야 하나요? |
| 사서 화면은 알아서 구성하면 되죠? | 사서 화면에 반납 예정일이 지난 도서 목록이 꼭 있어야 하나요? |
| 결과 형식은 적절히 하면 되죠? | 결과 CSV의 대출일 열은 YYYY-MM-DD 형식으로 내면 되나요? |

제안형 재질문("이 안으로 진행해도 되나요?")에 '제안해 주시면 검토하겠습니다'처럼 결론 없는 답이 오면, 선택지 2개 중 하나를 고르는 선택형으로 1회 더 묻습니다. 이 선택형 재질문도 재질문 1회로 `ask_count`에 포함합니다. 그래도 결론이 없으면 assumed로 기록하고 진행합니다. 같은 제안을 되풀이하지 않습니다.

재질문할 때의 원장 상태 전이:
- partial·unclear 행을 같은 행에서 다시 쓰면 status를 `open`으로 돌리고 `ask_count`는 그대로 둡니다. 보낼 때 `sent`로 바꾸고 `ask_count`를 1 올립니다.
- 새 행으로 쪼갰다면 원래 행은 `answered`(답한 부분만 decision에) 또는 `dropped`로 닫습니다. 닫지 않으면 원래 P0·P1 행이 미해결로 남아 멈춤 조건이 참이 되지 않습니다.
- 재질문 한도는 status가 partial·unclear이면서 `ask_count`가 3 이상일 때만 걸립니다. 세 번째 전송 뒤 답을 기다리는 `sent` 행과 보낼 차례인 `open` 행은 한도 판정에서 뺍니다.

- 멘트 유형별 양식: [질문 멘트 템플릿](../templates/QUESTION_MESSAGES.md)
- 답변 원장: [QUESTION_LEDGER.csv](../templates/QUESTION_LEDGER.csv) (status: open, sent, answered, partial, unclear, assumed, dropped). 선택 열 `ask_count`는 보낸 횟수(첫 질문 포함)이며, 비우거나 열이 없으면 0으로 봅니다.
- 후보 질문 초안: `python3 tools/question_candidates.py <파일.csv>... [--ref a.csv:열=b.csv:열]`([question_candidates.py](../tools/question_candidates.py))가 데이터에서 보이는 결정 지점(빈 칸, 0·음수, 단위 혼재, 공백·대소문자만 다른 ID, 중복 ID, 같은 시각, 참조 누락)을 원장 형식 행으로 출력합니다. 초안이므로 README로 답이 나온 것은 지우고, 목적·역할·화면·출력 형식 질문은 직접 더합니다.
- 원장 도구: `python3 tools/question_ledger.py lint|next|summary <원장.csv>` ([question_ledger.py](../tools/question_ledger.py), 키트 루트 기준. 과제 루트에서는 `.hackathon-kit/tools/...`처럼 키트 위치에 맞게 바꿈).
  - `lint`: 복합 질문·열린 표현·중복·재질문 한도(`retry_limit`, partial·unclear 행의 ask_count 3 이상)를 찾습니다. 질문 문장은 120자 안팎을 권장하고, `--max-length` 기본값 160은 질문 열 상한입니다. 25자 미만의 짧은 질문은 맥락까지 합쳐 중복을 비교합니다. 비슷한 문장(근사 중복) 비교는 같은 category 안에서만 하고, 한 category의 비교 대상이 500행을 넘으면 정확 중복만 확인합니다.
  - `next --format text`: open·partial·unclear 질문을 번호와 함께 출력합니다. partial(보완 질문)·unclear(재질문) 행은 원문을 그대로 복사용으로 내지 않고 '[다시 쓰기 필요: 쪼개기/선택지/샘플 행]'으로 표시합니다. 다시 쓴 뒤 status를 open으로 돌리면 고친 문장이 복사용으로 나옵니다. 재질문 한도에 이른 행은 목록에서 빼고 assumed 기록 대상으로 알려 줍니다.
  - `summary`: 미해결 P0·P1, 다시 쓸 행, 재질문 한도 도달 id를 보여 줍니다.

담당자 답변 원문은 출처와 함께 원장에 남기고 공식 규정으로 승격하지 않습니다.

## 실습

[방문 신청 의뢰](../exercises/visitor-review/BRIEF.md)를 읽고 첫 질문 3개를 쓰세요. 답변을 받은 다음 새 후속 질문 2개를 쓰고 [요구 연결표](../templates/REQUIREMENT_TRACEABILITY.md)의 한 행을 채웁니다. 진행자 자료는 먼저 답한 뒤 읽습니다.
