# 질문 사다리: 답변이 구현을 바꾸게 만들기

Notion의 문제 정의·운영진 인터뷰·워크북을 바탕으로 구성한 자체 준비법입니다. 실제 배점이나 정답 질문 목록이 아닙니다.

## 3라운드

| 라운드 | 묻는 목적 | 질문 예시 |
| --- | --- | --- |
| 1. 맥락 | 사용자·현재 절차·불편 파악 | 지금 누가 어떤 순서로 검토하며 어디서 실수가 자주 생기나요? |
| 2. 규정과 예외 | 처리 결과를 바꾸는 조건 확인 | 어느 문서가 우선이며, 누락·상충·중복은 누가 판단하나요? |
| 3. 완료 기준 | 최소 범위와 검수 사례 합의 | 필수 출력은 무엇이고 반드시 맞아야 할 정상·경계·예외 사례는 무엇인가요? |

처음부터 어려운 기술 용어로 묻지 않아도 됩니다. README에 명확한 것을 다시 묻거나 담당자에게 구현 순서 전체를 대신 정해 달라고 하지는 않습니다.

## 8칸 질문 지도

1. 왜 이 일이 필요한가?
2. 누가 언제 결과를 쓰는가?
3. 어떤 입력과 정상 예시가 있는가?
4. 무엇이 승인·반려·보류를 결정하는가?
5. 문서 충돌·정보 누락·실패는 어떻게 다루는가?
6. 결과의 형식·이유·내보내기 중 무엇이 필수인가?
7. 반드시 확인할 대표 사례는 무엇인가?
8. 필수·제외·미정의 정리가 맞는가?

모든 칸을 정해진 개수만큼 묻는 시험이 아닙니다. 이미 주어진 사실은 사용하고, 구현 방향이 바뀌는 질문을 먼저 고릅니다.

## 답변에 따른 후속 질문

| 받은 답변 | 이어서 확인할 것 | 구현에 주는 영향 |
| --- | --- | --- |
| '최대 4명' | 본인을 포함한 수인가, 0명·문자·빈값은? | 숫자 변환과 경계·오류 상태 |
| '최신 문서 우선' | 무엇을 기준으로 최신인가, 시행일과 예외는? | 버전·적용일 선택 |
| '중복은 제외' | 중복 키는 무엇인가, 내용이 다른 중복도 같은가? | 중복 제거와 상충 보류 구분 |
| '이유도 필요' | 행별 이유인가, 요약만인가, 원 식별자는? | 결과 스키마와 추적 가능성 |
| '화면이면 됨' | 어떤 조작이 반드시 가능해야 하는가? | 입력·필터·오류 안내·저장 범위 |
| 답변이 없음 | 해당 불확실성을 보류로 표시해도 되는가? | 임의 승인·반려 대신 미정 유지 |

## 질문에서 구현까지 한 줄로

**질문 → 담당자 답 → 확정 규칙/남은 모호함 → 바뀐 기능 → 기대 사례**

자체 예: '중복이면?' → '같은 ID의 다른 내용은 사람이 검토' → '둘 중 하나를 덮어쓰지 않음' → '상충 상태와 원행 보존' → '같은 ID 두 값의 예상 결과를 먼저 정함'.

질문을 많이 했다는 사실보다 어떤 결정이 바뀌었는지 설명할 수 있는지가 중요합니다.
