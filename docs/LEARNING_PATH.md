## 1. 문제를 정의한다는 것

'엑셀을 자동화한다'는 방법입니다. 해결할 문제는 '담당자가 신청서를 검토하는 데 오래 걸리고, 규정 해석이 달라 같은 신청의 결과가 바뀐다'처럼 실제 불편과 판단의 실패를 말합니다.

다음 다섯 문장을 먼저 채웁니다.

1. 누가 사용하는가?
2. 현재 무엇 때문에 시간이 들거나 오류가 나는가?
3. 어떤 입력과 규칙을 받는가?
4. 사용자가 어떤 결과를 보고 다음 행동을 해야 하는가?
5. 무엇을 관측하면 해결했다고 말할 수 있는가?

예를 들어 장비 대여 의뢰를 받았다면 'DB는 무엇을 쓸까요?'보다 '동일 장비를 여러 사람이 같은 날짜에 신청하면 무엇을 우선합니까?'가 설계를 바꾸는 질문입니다. 상대가 답하지 않은 규칙을 AI의 상식으로 확정하지 않습니다.

**직접 해보기:** 모호한 의뢰를 한 문장으로 다시 쓰고, 결과를 바꿀 질문 4개를 중요도순으로 적습니다.

## 2. 개발의 최소 구조

작은 프로그램은 대체로 **입력 → 형식 확인 → 업무 규칙 → 결과 → 사용자 행동**으로 설명할 수 있습니다.

- 입력: 파일, 텍스트, 화면의 폼. 확장자와 실제 내용이 항상 일치하지는 않습니다.
- 형식 확인: 필수 열·자료형·날짜·단위·빈값·중복을 확인합니다.
- 업무 규칙: '최대 4명', '기간 겹침', '우선순위' 같은 도메인 판단입니다.
- 결과: 승인·반려·보류, 그 이유, 원래 행을 찾을 식별자처럼 사용자가 쓸 수 있는 형태입니다.
- 오류: 잘못된 입력을 정상 결과처럼 처리하지 않고, 고칠 수 있는 메시지와 상태를 반환합니다.

형식 오류와 업무상 반려를 구분하면 원인을 설명하기 쉬워집니다. 규칙을 데이터와 섞어 임의로 덮어쓰면 재현이 어려워집니다.

**직접 해보기:** '인원 누락'과 '상한 초과'가 같은 오류인지 설명하고, 규정에 근거가 없을 때 담당자에게 무엇을 물을지 적습니다.

## 3. 프런트엔드·백엔드·데이터 저장을 고르는 법

프런트엔드는 사용자가 보고 조작하는 화면, 백엔드는 처리·규칙·API, 저장소는 상태를 보관하는 곳입니다. 파일 보고서만 요구되면 세 가지를 모두 만들 필요는 없습니다.

| 필요한 행동 | 작은 선택의 예 | 추가 판단 |
| --- | --- | --- |
| CSV를 한 번 읽고 보고서 출력 | 기존 런타임의 파일 처리 | 다시 실행할 때 입력·출력이 보존되는가 |
| 사용자가 입력하고 즉시 결과 확인 | 단순 화면과 규칙 함수 | 오류 메시지·버튼·접근성 |
| 여러 사용자가 같은 상태 수정 | 서버·저장소 필요성을 검토 | 동시성·식별자·권한·중복 요청 |
| 영구 저장 요구가 없음 | 임시 메모리/파일 여부를 명시 | 새 DB를 넣는 비용이 가치보다 큰가 |

'유명한 기술'이 선택 이유가 되지는 않습니다. '현재 요구가 읽기 전용이고 180분 내 제출해야 하므로 기존 스택을 유지했다'처럼 요구와 비용을 연결합니다. 반대로 영구 저장이 필수라면 단순하다는 이유로 그 요구를 빼면 안 됩니다.

**직접 해보기:** 장비 대여 요청을 처리하는 데 로그인·결제·추천 AI가 왜 필요하거나 불필요한지 각각 한 문장으로 적습니다.

## 4. AI에 잘 맡기는 방법

배경·목표·자료·제약·출력·판단 기준을 전달하되 한 번에 거대한 설계를 요구하지 않습니다. 확정 규칙과 질문 중인 규칙을 표시하면 AI가 빠진 조건을 임의로 채우는 일을 줄일 수 있습니다.

- 첫 지시: 읽을 파일, 실제 목표, 수정 범위, 첫 기능.
- 후속 지시: 바뀐 규칙 또는 관측된 오류만.
- 중지 조건: 권한·도구 제한, 원인 불명 요청, 제출 시간이 부족할 때.
- 결과 확인: 파일·명령·출력·한계. '끝났다'는 자연어 자체는 증거가 아닙니다.

[결정 기록](../templates/DECISIONS.md)은 바뀐 판단만 남깁니다. 기록을 쓰느라 구현 시간이 사라지지 않게 짧게 유지합니다.

## 5. 검증 사고와 현재 검사 권한

규정이 '최대 4명'이면 3·4·5명은 서로 다른 사례입니다. 정상만 보고 '다 됐다'고 하지 않습니다. 누락·중복·상충 규칙·잘못된 날짜도 결과가 달라져야 할 수 있습니다.

기대값은 테스트를 실행한 뒤 맞추는 것이 아니라 먼저 확정합니다. 오류 수정 전후에는 같은 입력으로 비교해야 변화의 원인을 설명할 수 있습니다. 현재 모델이나 플랫폼이 검사를 금지하면 그 범위를 실행하지 않고 **NOT_RUN**으로 남깁니다.

| 구분 | 의미 |
| --- | --- |
| 코드상 예상 | 실행 전 생각. 통과 결과가 아님 |
| 실제 명령 결과 | 그 명령·입력에 대해 관측한 사실 |
| 수동 Browser 결과 | 참가자가 확인한 특정 화면·행동 |
| 미실행 | 부족한 증거를 명시한 상태 |

**직접 해보기:** 'HTTP 200이면 화면 버튼도 정상이다'가 왜 성립하지 않는지 설명합니다.

## 6. 시간과 토큰

모든 Skill을 읽히거나 여러 에이전트를 띄우는 것이 목표가 아닙니다. 최소 기능이 빨리 관측되고, 오류를 좁혀 고치며, 자기 결과물을 설명할 수 있어야 합니다.

Goal이 없으면 일반 지시문에 목표·완료 증거·중지 조건을 적으면 됩니다. 병렬 기능이 없으면 단일 작성자로 진행합니다. MCP가 없어도 제공된 CLI 도구로 많은 파일 작업을 할 수 있습니다. 기능 부재를 준비 전체의 중단으로 확대하지 않습니다.

정확한 토큰 한도·공식 가중치를 모르면 숫자를 만들어내지 않습니다. 한 오류를 조사할 때 필요한 파일과 메시지만 추가하고, 막연한 '전부 다시 분석' 요청을 반복하지 않습니다.

## 7. 운영진 인터뷰를 실제 행동으로 바꾸기

보관된 대화의 인터뷰 목차와 해설에서 얻은 준비 관점입니다. 영상을 이번 작업에서 새로 시청한 것은 아니며, 인터뷰의 일반 환경을 이번 대회의 규칙으로 사용하지 않습니다.

- 04:20 AI Literacy/Native: 도구 이름 암기보다 업무 흐름의 어느 부분을 바꿀지 판단합니다.
- 10:57 평가 방식, 15:47 질문법: 업무 담당자의 목적과 예외를 끌어냅니다.
- 20:34 비용·효율: 적은 호출 자체보다 필요한 호출로 결과를 얻는가를 봅니다.
- 22:16 결과물·AI 활용·이해도: 실제 산출물, 지시 이유, 본인 설명을 연결합니다.
- 30:43 Skill 재사용: 공개된 방법을 현재 문제에 맞게 선택합니다.
- 33:22 비개발 참가자 사례: 현장의 문제 이해가 장점이 될 수 있습니다. 개발 지식이 전혀 필요 없다는 뜻은 아닙니다.

'평가 에이전트가 몇 명이니 이렇게 채점된다'거나 '이 순서면 합격한다'는 식으로 공식 배점과 성공을 추정하지 않습니다.

## 시간별 경로

**20분:** Cofa 기준 → 첫 지시문 → 질문 4개 → 직접 설명 한 번. 새 도구 설치는 생략합니다.

**60~90분:** 가상 의뢰 10분 → 규칙·MVP 15분 → 허용된 작은 구현 30분 → 증거와 설명 15분. 실제 하지 못한 항목은 미실행으로 남깁니다.

**하루:** 학습 01~08 → 장비 점검과 체험 계획 → 통합 모의 → AI 없이 설명 연습. 준비 자료 완성과 학습 완료를 같은 체크박스로 기록하지 않습니다.

**시험 당일:** 실제 안내·준비·시작·제출 절차가 모든 자체 시간표보다 우선합니다. 노션 공부 진도나 과거 연습 성공을 현재 환경 작동의 증거로 대신하지 않습니다.
