# 180분 작업 운영 매뉴얼

실제 과제의 최신 지시가 우선입니다. 다음 시간표는 **자체 계획 예시**이며 공식 단계별 시간 배분이나 채점 기준이 아닙니다.

## 먼저 네 역할을 구분하기

| 상대/도구 | 맡길 일 |
| --- | --- |
| 참가자 | 실제 문제, 우선순위, 업무 결정, 최종 제출과 설명 |
| 업무 담당자 | 사용자의 목적·업무 규칙·예외·완료 기준 질문 |
| 제공 Codex | 확정한 요구의 구현, 허용된 파일 작업과 검사 |
| Cofa Helper/공식 문의 | 환경 사용법, 제출 동선, 플랫폼·감독 장애 |

업무 규칙을 Codex의 추측으로 확정하지 않고, 환경 오류를 업무 담당자의 판단으로 해결하려 하지 않습니다.

## 시간표

| 경과 | 우선 산출물 | 다음 단계 기준 |
| --- | --- | --- |
| 0~15분 | README·파일·자료·필수 출력 파악 | 목표, 사용 주체, 입력, 제출 경로가 구분됨 |
| 15~30분 | 담당자 질문·규칙·필수 기능 확정 | 결과를 바꾸는 모호함과 미확정 사항이 기록됨 |
| 30~110분 | 입력→처리→출력의 첫 실행 가능한 기능 | 핵심 흐름을 설명할 수 있고 실제 상태가 기록됨 |
| 110~150분 | 필수 요구 보완·허용 검사·오류 수정 | 정상·경계·누락·충돌과 회귀의 증거 또는 NOT_RUN |
| 150~170분 | 파일·실행법·선택 이유·미완료 정리 | 새 기능 추가보다 제출 안정성을 우선함 |
| 170~180분 | 공식 절차에 따른 저장·제출 | 확정 화면과 최종 제출 절차를 직접 수행함 |

첫 실행 가능한 산출물이 늦으면 UI 꾸미기·병렬화·새 MCP·의존성 추가부터 줄입니다. 시간 종료 직전 리팩터링을 시작하지 않습니다. 후속 30분과 대기 시간을 과제의 여분 30분으로 사용하지 않습니다.

## 1. 요구사항부터 분해

- '누가 무엇을 결정하거나 처리하기 위해 쓰는가?'
- '제공 파일과 규정 중 어느 버전이 우선인가?'
- '정상·중복·누락·상충 입력은 어떤 결과여야 하는가?'
- '필수 출력의 형식·정렬·저장 위치와 완료 예시는 무엇인가?'
- '지금 하지 않아도 되는 기능은 무엇인가?'

답에 따라 구조가 달라지는 질문을 먼저 묶어 묻고, 새 답변이 들어오면 관련 규칙만 갱신합니다. 이미 확인된 사항을 다시 묻지 않습니다.

## 2. Codex에 맡길 작업 단위

    배경: [사용자와 업무 문제]
    목표: [이번 작은 기능]
    자료: [현재 루트의 실제 파일과 확정 규칙]
    제약: [수정 범위, 금지 동작, 시간·데이터 경계]
    출력: [필수 파일/형식과 사용자 행동]
    판단·검사: [정상/경계/실패의 기대값, 허용된 검사 범위]

한 번에 전체 과제를 반복 전송하지 않습니다. 오류가 나면 실제 오류·관련 파일·기대 결과만 전달합니다. 한 파일의 작성자는 한 명으로 유지합니다.

## 3. 구현과 판단의 연결

정상 입력 하나가 끝까지 지나가는 작은 경로부터 만듭니다. 데이터가 읽히는지, 규칙이 결정되는 위치가 어디인지, 출력과 오류가 사용자에게 어떻게 보이는지 설명할 수 있어야 합니다. 실제 과제가 화면을 요구하지 않으면 웹앱부터 만들지 않습니다.

## 4. 허용된 검사의 증거

[증거 양식](../templates/EVIDENCE.md)에 요구사항 → 입력 → 기대값 → 실행 명령 → 실제 결과를 연결합니다. 현재 모델·플랫폼 정책이 금지한 검사는 실행하거나 다른 에이전트에 맡기지 않습니다. 실행하지 않은 것은 NOT_RUN입니다.

정책상 실행이 허용된 경우 실패 사례를 좁게 재현하고, 원인을 근거로 수정한 뒤 같은 사례와 관련 회귀 사례를 사용합니다. 한 조건을 봤다고 전체 동작 통과로 확대하지 않습니다. 코드상 예상·HTTP 응답·참가자의 수동 Browser 관측을 구분합니다.

## 5. 시간·토큰 운용

- 기본은 제공된 단일 Codex입니다. /goal이나 subagent를 여는 데 시간을 쓰지 않습니다.
- 지원·허용된 Goal을 쓰더라도 완료 기준·시간 한도·중지 조건을 함께 둡니다.
- 병렬이 필요하고 실제 허용될 때만 독립적인 작은 읽기 작업을 나눕니다. 같은 파일을 여러 작업자에게 맡기지 않습니다.
- 토큰 수치나 '짧은 답변=높은 점수'를 만들어내지 않습니다. 반복 전체 문맥·필요 없는 도구 설정·동일 실패 재시도를 줄입니다.
- 실제로 전송됐는지 모르는 요청을 다시 보내지 않고 원 상태를 먼저 확인합니다.

## 6. 제출과 후속 설명

[제출 직전 양식](../templates/PRE_SUBMISSION.md)을 사용합니다. 파일 저장, 필수 경로, 실행법, 실제 증거, 남은 한계와 차용 자료를 정리한 뒤 공식 화면에서 직접 제출합니다. 제출물 확정 후 수정이 반영된다고 추정하지 않습니다.

**실제 AI 금지 후속 단계에서는 AI 호출·도구 답안 생성·미리 쓴 답 복사 없이 직접 답합니다.** 본 문서의 설명 연습은 그 단계 전에만 합니다.
