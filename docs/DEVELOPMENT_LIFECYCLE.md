# 요구 이해부터 개발·검토·최종 인계까지

권장 흐름은 **요구·가이드·현업 확인 → 데이터 이해와 목표 → 지침·환경·계획 → 작은 기능 위임 → 주요 기능마다 설명·논의·보완 → 실제 확인·원인 분석 → 코드·구조 검토 → 최종 인계**입니다. 문서가 있다는 사실과 기능이 완료됐다는 사실은 구분합니다. 필요한 검사와 실행이 허용된 범위에서 실제 결과를 확인하고, 남은 문제가 있으면 담당자·해제 조건을 적습니다.

새 정본을 여러 벌 만들지 않습니다. 기존 SPEC/README/계획이 있으면 그것을 연결합니다. 작은 수정은 기존 문서의 한 절로 충분합니다. 구현을 승인받았으면 아래 절차를 위해 매번 허락을 다시 묻지 않고 계속합니다. 범위·업무 규칙·외부 공개 등 결과를 바꾸는 선택만 사람에게 확인합니다.

## 1. 요구·현업·데이터·목표를 먼저 연결

[안전한 시작](SAFE_WORKROOM_START.md)으로 최초 상태를 남긴 후 원본 README·지침·데이터를 읽습니다. 데이터는 행 하나의 의미, 열·단위·범위, 키·조인, 결측·중복, 기준 시점, 파일 간 충돌을 확인합니다. 원본은 보존하고 허용된 로컬 문서에 통계와 출처를 기록합니다.

현업에는 결과를 바꿀 업무 사실 하나씩 묻습니다. 목표·필수 출력·예외·수용 조건·제외 범위를 확정하고 실제 답변과 가정을 나눕니다. 알고리즘은 목표·입력 규모·제약을 확인한 후 고릅니다. [질문 운영서](STAKEHOLDER_QUESTIONS.md)와 기존 질문 원장을 재사용합니다.

연결 단위는 **요구 ID → 출처/현업 답 → 목표·완료 기준 → 설계 결정 → 파일/함수 → 실제 검사·사용자 확인**입니다. 보류된 업무 사실이 있으면 그 사실에 의존하지 않는 작업부터 진행합니다.

## 2. 지침·환경·계획을 실행 가능한 크기로

`workroom.py init`이 만드는 `.cofa-workbench/docs/DEVELOPMENT_PLAN.md`에 다음을 적습니다.

- 목표·이번 범위·제외 범위와 관측 가능한 완료 기준. 파일 생성·설치·실행·실사용을 구분.
- 원본 지침·명세·데이터 사전의 위치와 이번 작업 규칙. 원본 AGENTS.md나 전역 설정을 자동으로 덮어쓰지 않음.
- 실제 런타임·의존성·허용 명령·입출력·설치/실행/중지/복구. 비밀 값 대신 설정 이름만 기록.
- 데이터/상태 소유자·API·모듈 경계와 선택 이유·대안. 작은 앱에 DB·서버·계층을 기계적으로 추가하지 않음.
- 첫 유용한 기능 → 다음 의존 작업 → 주요 단계별 확인. 담당 파일·완료 기준·확인 방법·다음 담당.

시간표는 필요할 때만 만듭니다. 실제 환경에서 지원·허용되는 경우에만 여러 세션을 사용합니다. 지원되지 않으면 단일 세션으로 같은 순서를 진행합니다.

## 3. 위임·멀티세션 handoff

조정자는 `AGENT_ASSIGNMENTS.md`에서 Git root·파일·공유 데이터·배포 효과의 작성권을 배정합니다. 파일별 한 작성자를 유지하고 다른 세션은 읽기 검토를 합니다. 역할 이름이 달라도 같은 파일을 동시에 고치지 않습니다.

각 세션에 목표, 정확한 입력/출력·파일, 제외/금지, 현재 완료/미완료, 실제 확인 방법, 중지 조건을 넘깁니다. [세션 인계 양식](../templates/AGENT_HANDOFF.md)을 허용된 작업실 아래 세션별 파일로 사용합니다. 예: `.cofa-workbench/docs/handoffs/worker-a.md`. 같은 경로는 해당 작성자만 수정합니다.

인계에는 기준 revision/dirty, 수정 파일, 실제 실행·실패, 미실행, 열어 둔 프로세스·복구, 다음 한 행동과 작성권 반환 여부를 담습니다. 다음 세션은 접수와 실제 착수를 구분하며 이미 끝난 작업·불명 전송을 반복하지 않습니다. 통합은 조정자가 차이를 검토해 수행합니다.

## 4. 주요 기능마다 대화하며 보완

버튼 하나·파일 하나마다 전체 보고하지 않습니다. 첫 입력→처리→출력, 핵심 알고리즘·역할 분리, 통합 동작처럼 사용자가 판단할 수 있는 단위에서 보고합니다. `MILESTONE_REVIEW.md`와 기존 Workroom 이벤트를 사용합니다.

보고 순서: **무엇이 가능해졌나 → 어떻게 만들었나/선택 이유 → 실제 결과·근거 → 남은 문제·대안 → 사람이 결정할 것 → 다음 개발**. 업무 정책 결정이 없으면 승인된 계획의 다음 작업을 계속합니다.

대화에서 요구가 바뀌면 영향받는 요구·설계·코드·검사만 함께 수정합니다. '추가로 필요할 수 있음'과 이번 완료에 필수인 것을 구분하고, 후속 제안을 전부 이번 범위로 확대하지 않습니다. 구현자 보고를 독립 검증이나 사람의 확정으로 승격하지 않습니다.

## 5. 실제 확인·안 되는 기능·원인 분석

허용된 범위에서 정상·경계·잘못된 입력·충돌·회귀를 검사합니다. 화면은 사용 환경의 공식 Browser로 사용자가 직접 확인합니다. 에이전트는 관측하지 않은 화면을 통과했다고 말하지 않습니다. [수동 확인 절차](WEB_IDE_TERMINAL_ONLY.md)와 `manual-preview-validation` Skill을 사용합니다.

- 확인 흐름: 열기 → 입력/선택 → 실행 → 결과/오류 → 저장/재열기. 역할별 접근·비활성·로딩·포커스·빈 상태도 요구에 맞게 확인.
- 실패 기록: 재현 입력/조작, 기대값, 실제값, 환경/revision, 영향을 받는 요구. 원인 **가설**과 확인된 원인을 분리.
- 수리: 가장 작은 변경 → 같은 실패 사례 → 영향받는 기존 정상 사례 재확인. 환경·근거가 바뀌지 않았으면 같은 검사를 무한 반복하지 않음.
- 실행 불가: NOT_RUN/BLOCKED와 이유·재개 조건·담당. HTTP 200·프로세스 생존만으로 업무 성공을 확정하지 않음.

## 6. 클린 코드·구조는 구체적으로 검토

클린 코드라는 이름으로 전체 재작성을 하지 않습니다. `QUALITY_REVIEW.md`에 항목별 **파일/함수 + 문제·영향 + 필요한 조치 + 근거/미검증**을 남깁니다. 기능 요구를 충족하고 실제로 유지보수하기 쉬운 구조인지 판단합니다.

| 코드 품질 | 구조 품질 |
| --- | --- |
| 이름이 업무 뜻을 표현하는가 | UI·업무 규칙·입출력 책임이 필요한 만큼 구분되는가 |
| 함수가 한 책임을 갖고 읽히는가 | 데이터와 확정 상태의 소유자가 분명한가 |
| 같은 규칙이 여러 곳에서 달라지지 않는가 | 의존 방향·API·스키마와 변경 영향이 설명되는가 |
| 입력·단위·실패·예외를 명시적으로 다루는가 | 권한을 화면 밖의 처리 경계에서도 강제하는가 |
| 비밀·개인자료가 출력/로그에 새지 않는가 | 저장·중단·복구가 요구한 수준으로 되는가 |
| 변경을 검증할 정상·실패 근거가 있는가 | 현 규모에 불필요한 추상화·계층·서비스가 없는가 |

관측된 결함과 취향을 분리합니다. 미사용 코드 정리·리팩터링은 이번 작업의 변경만 대상으로 하며 사용자/타인의 변경을 보존합니다. 회귀 위험이 큰 선택 정리는 다음 작업으로 남길 수 있습니다. 독립 검토자가 없으면 자기 검토라고 표시합니다.

## 7. 최종 개발명세·handoff와 완료 조건

새 최종본을 무한히 만들지 않습니다. 기존 명세에는 실제 구현 계약을 갱신하고, 작업실 `HANDOFF.md`에는 현재 revision, 완성 기능·제외/미완료, 구조·데이터 흐름, 실행/설치/중지/저장/복구, 확인 근거, 알려진 문제·다음 담당을 연결합니다. `FINAL_EXPLANATION.md`는 사전 이해 점검용이며 운영 인계와 다릅니다.

완료 판단:

- 합의한 필수 요구와 실제 구현·출력이 연결되고, 허용된 필수 검사·실사용 확인이 끝났는가?
- 사용자가 어떻게 쓰고 확인·중지·복구하는지 알 수 있는가?
- 중요한 실패·보안·데이터 위험이 해결됐거나 미완료로 드러나 있는가?
- 다음 사람이 정확한 파일·명령·근거를 따라 재개할 수 있고 작성권이 정리됐는가?

하나라도 필수 조건이 남으면 부분 완료와 다음 담당을 적습니다. 문서를 썼다는 이유로 '전체 완료'로 바꾸지 않습니다. 실제 AI 금지 단계가 시작되면 구현·해설·답안 메모 생성을 중단합니다.

## 시작 프롬프트

```text
내가 전달한 요구·공식 지침·현업 답변과 현재 파일을 기준으로
이 키트의 docs/DEVELOPMENT_LIFECYCLE.md를 적용해라.
먼저 데이터와 목표·필수 완료 기준을 맞추고 기존 명세·환경·계획을 연결해라.
승인된 범위의 작은 완결 기능을 자율적으로 개발하고,
주요 단계마다 어떻게 만들었고 무엇이 더 필요한지 실제 근거로 설명해라.
여러 세션이 허용되면 파일별 한 작성자를 정하고 세션 handoff를 남겨라.
화면 확인은 내가 하고, 실패는 재현·원인 분석·최소 수리·회귀 확인으로 처리해라.
클린 코드/구조를 근거로 검토하고 실제 구현 명세·최종 HANDOFF를 갱신해라.
금지되거나 못 한 검사는 미실행으로 남기고 실제 AI 금지 단계에는 중단해라.
```
