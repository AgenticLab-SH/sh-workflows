# 최소 구현과 구조 선택

Notion의 개발 기초·외부 풀스택 세미나·운영진 인터뷰에서 도출한 준비용 판단표입니다. 특정 기술·배포 방식이 시험 필수라는 뜻이 아닙니다.

## 최소라는 말의 뜻

MVP는 **핵심 업무를 끝까지 처리하는 가장 작은 결과물**입니다. 필수 오류 처리나 필수 화면을 빼는 뜻은 아닙니다. 입력이 있고, 확인된 규칙을 적용하고, 사용자가 쓸 수 있는 출력이 있어야 합니다.

| 결정 | 작은 선택 후보 | 더 큰 구조가 필요한 단서 |
| --- | --- | --- |
| 스크립트/웹앱 | 일회성 파일 처리라면 단일 명령 | 사용자가 반복 입력·검토·수정하는 화면이 필수 |
| 파일/DB | 읽기 위주·소량·단일 실행 | 장기 저장·동시 수정·검색·무결성 요구 |
| 단일 앱/분산 | 한 기능·제한된 시간·하나의 실행 | 독립 확장·배포·장애 격리가 실제 필수 |
| 동기/비동기 | 짧고 즉시 끝나는 처리 | 오래 걸리는 작업과 재시도·상태 관리 필요 |
| 조회/쓰기 | 원본 읽기와 결과 파일 분리 | 데이터 변경·중복 요청·승인 이력 요구 |
| 인증·접근통제 | 실제 노출 범위에 비례 | 민감한 자료·사용자별 접근 구분 |
| 외부 배포 | 내부 실행·제출이면 불필요 | 과제와 정책이 외부 공개를 명시적으로 요구 |

읽기 전용이라고 모든 보안을 없애지 않습니다. 반대로 조회만 하는 작은 도구에 쓰기 충돌 방지용 복잡한 분산 구조를 넣을 이유도 별도로 설명해야 합니다.

## 7개 결정 질문

사용자 가치는 무엇인가? 입력과 규칙의 진실은 무엇인가? 필수·선택·제외는 무엇인가? 데이터가 어떻게 흐르는가? 잘못된 입력이나 변경은 어떤 피해가 있는가? 무엇으로 성공을 판단하는가? 시간·실행·유지 비용이 요구에 비례하는가?

## 구조를 설명하는 최소 언어

- **프런트엔드:** 입력과 결과를 보여주고 사용자의 행동을 받음.
- **백엔드/처리 함수:** 자료 검증, 업무 규칙, 응답과 실패를 처리.
- **저장:** 파일·메모리·DB 중 어느 것이 언제까지 남는지.
- **API:** 요청 필드·응답 형식·상태·읽기/쓰기의 약속.
- **오류 처리:** 형식 오류·업무 반려·판단 보류·시스템 실패를 구별.
- **실행과 관측:** 서버/명령의 시작과 실제 사용자의 결과가 어떻게 연결되는지.

## '주장 → 이유 → 근거 → 한계'

자체 예: '단일 스크립트를 선택했다 → 한 번 처리하는 CSV 보고서이기 때문 → 정한 정상·경계 사례를 허용 범위에서 관측 → 여러 사용자의 동시 수정은 미구현'. 실제 관측을 하지 않았다면 근거 칸은 NOT_RUN입니다.

[결정 기록](../templates/DECISIONS.md)에 이 한 줄만 남겨도 됩니다. 미래의 모든 확장 가능성을 적느라 첫 결과물이 늦어지지 않게 합니다.

## 무엇을 버릴까

도구 이름을 기준으로 무조건 빼지 않습니다. 현재 필수 요구에 기여하는지, 실제 위험을 줄이는지, 남은 시간 안에 실행·설명할 수 있는지, 더 간단한 대안이 있는지로 판단합니다.

학습용 예: 3명이 읽는 작은 보고 도구에 Kubernetes·다중 DB·4개 서비스를 제안받으면 각각 해결하는 요구를 물어봅니다. 필요한 근거가 없다면 단일 처리 경로부터 만듭니다.
