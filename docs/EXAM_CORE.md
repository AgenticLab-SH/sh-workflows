# 시험 핵심 운영서

**이 문서부터 읽습니다.** 2026-10-31 Cofa 2차를 준비하며 읽은 Notion 학습자료 18개와 관련 정본·연구자료를 공개 준비용으로 재구성했습니다. 원 Notion 전체를 복제한 자료가 아닙니다. 규칙의 근거는 [Cofa 기준](COFA_2026_BRIEF.md), 읽은 범위는 [Notion 반영표](NOTION_COVERAGE.md)에 있습니다.

시험장에서는 제공된 환경과 최신 지시가 우선입니다. 이 자료를 읽거나 GitHub를 게시한 사실은 실제 체험·학습·동작 확인의 완료가 아닙니다.

## 먼저 기억할 흐름

**업무 목적 읽기 → 담당자에게 필요한 사실 질문 → 필수 범위 선택 → 제공 AI에 작은 구현 위임 → 허용된 근거 확인 → 저장·파일 확정 → 직접 설명 → 최종 완료**

과제 시간은 최대 180분이고 후속 서술형은 별도 총 30분입니다. 대기 시간도 전체 종료 시각 안에 들어갑니다. 파일 확정만으로 응시가 끝나는 것은 아닙니다. 상세 후속 형식은 Notion의 가이드 해설에 6문항×각 5분으로 정리되어 있으며 실제 공지를 따릅니다.

## 1. 사용자를 먼저 찾기

'CSV 자동화'는 구현 방법이지 해결할 업무 문제 자체는 아닙니다. 다음 한 문장을 먼저 채웁니다.

> [사용자]가 [현재 어떤 판단/작업]을 하면서 [시간·오류·일관성 문제]를 겪으므로, [입력]에서 [필요한 결과와 후속 행동]을 얻도록 만든다.

예: 담당자가 방문 신청을 검토할 때 문서 해석이 달라진다면 '예쁜 신청 화면'보다 판정 규칙과 보류 이유가 먼저입니다. 실제 의뢰가 화면을 필수로 요구하면 화면을 빼도 된다는 뜻은 아닙니다.

## 2. 상대별로 질문을 나누기

| 대상 | 적합한 질문 | 넘기지 않을 판단 |
| --- | --- | --- |
| 업무 담당자 | 사용자, 업무 흐름, 규정, 예외, 출력, 검수 사례 | 어떤 프레임워크가 정답인지·할 일을 전부 정해 달라는 요청 |
| 제공 Codex | 파일 파악, 대안 비교, 확정 범위 구현, 허용 검사, 오류 조사 | 사업 규칙의 임의 확정 |
| Cofa Helper | 화면·터미널·Browser·제출 방법 | 업무 승인 규칙의 결정 |
| 공식 문의 | 플랫폼·AI·감독·저장 장애의 시각과 증상 | 신고하면 타이머가 멈춘다는 추정 |

[질문 사다리](STAKEHOLDER_QUESTIONS.md)를 참고해 핵심 모호함만 먼저 해소합니다. 답을 듣고 후속 질문과 설계를 바꿔야 합니다.

## 3. 질문을 요구사항으로 바꾸기

질문 목록만 쌓지 않고 답이 바꾼 구현을 적습니다.

| 사실/결정 | 바뀌는 구현 | 무엇으로 확인할까 |
| --- | --- | --- |
| 신청 최대 4명이라는 합성 규칙 | 인원 경계 분기 | 4명과 5명의 기대 결과 비교 |
| 중복 기준 미확정 | 임의 덮어쓰기 대신 보류 후보 | 담당자 확인 전 결과는 미정 표시 |
| 담당자에게 이유가 필수 | 원 식별자와 판정 사유 출력 | 어떤 입력 때문에 어떤 이유가 나왔는지 추적 |

위 수치는 자체 예시입니다. 실제 규정으로 복사하지 않습니다. [요구 연결표](../templates/REQUIREMENT_TRACEABILITY.md)에는 확정 사실·가정·미확정을 분리합니다.

## 4. 설명할 수 있는 작은 구조를 선택하기

입력 → 형식 확인 → 규칙 → 상태와 이유 → 사용자 행동이 이어지는 첫 기능을 만듭니다. 화면·DB·외부 배포가 필요하다고 확인되지 않았다면 도구부터 늘리지 않습니다.

- 파일 한 번 처리: 기존 런타임의 단일 스크립트가 후보입니다.
- 반복 입력과 화면 확인: 작은 앱과 처리 함수를 분리하는 것이 후보입니다.
- 동시 수정·영속성·접근 분리가 필수: 필요한 저장과 보호를 설계합니다.
- 읽기 전용이어도 입력 검증과 실제 필요한 접근통제는 생략하지 않습니다.

선택 이유는 '작아서'가 아니라 **현재 요구, 위험, 남은 시간, 확인 가능한 범위**로 설명합니다. [구조 판단표](MVP_DECISIONS.md)에 비교 기준이 있습니다.

## 5. Codex에는 단계별로 맡기기

배경·목표·자료·제약·출력·판단 기준을 전달합니다. 첫 요청에 과제 전체를 복사해 무제한 반복시키기보다, 읽기 → 첫 기능 → 관측한 오류 수정 → 제출 정리를 나눕니다.

승인 대기는 사용자의 선택이 필요한 상태, 실행 중은 중복 발신을 피할 상태, 응답 완료는 결과를 판단할 상태입니다. '완료했습니다'라는 말 자체는 증거가 아닙니다.

[단계별 지시문](DELEGATION_PROMPTS.md)을 현재 과제의 사실로 채우고, 필요한 Skill 1~2개만 읽힙니다. 지원되지 않는 /goal·병렬·MCP 때문에 전체 작업을 멈추거나 설정을 바꾸지 않습니다.

## 6. 증거의 수준을 구분하기

| 수준 | 확인한 것 | 아직 증명하지 못하는 것 |
| --- | --- | --- |
| 0 | AI가 완료라고 보고 | 파일 존재나 실행 |
| 1 | 실제 저장 파일 | 실행 성공 |
| 2 | 명령 종료·HTTP 응답·특정 화면 | 업무 규칙의 정확성 전체 |
| 3 | 정한 입력에서 기대값과 실제 결과 일치 | 다른 입력·수정 이후 결과 |
| 4 | 실패 수정 후 같은 사례와 관련 회귀 관측 | 검사하지 않은 기능 전체 |

현재 모델·플랫폼 정책이 검사를 금지하면 그 범위를 실행·위임하지 않고 **NOT_RUN**으로 표시합니다. 반례를 생각한 것과 반례를 실행한 것은 다릅니다.

[근거와 오류 대응](EVIDENCE_AND_RECOVERY.md)은 실패 입력·기대·실제·원인·수정·남은 한계를 연결합니다. 참가자의 수동 Browser 관측은 코드 검사나 HTTP 응답과 따로 적습니다.

## 7. 저장과 제출을 구분하기

에디터의 미저장 버퍼는 CLI가 못 읽을 수 있습니다. 외부 변경 경고가 뜨면 에디터 내용과 실제 저장 파일을 비교해 필요한 양쪽 변경을 보존합니다. Git의 U/M은 파일 추적·변경 표시일 수 있으므로 그 글자만으로 디스크 저장 여부를 단정하지 않습니다.

제출 미리보기는 모든 파일을 보여주지 않을 수 있습니다. 필수 경로와 실제 저장 파일을 먼저 알아야 합니다. **저장 → 미리보기 → 제출물 확정 → 질문 대기 → 후속 직접 답변 → 최종 완료 표시**는 다른 단계입니다.

[제출·장애 운영](SUBMISSION_AND_INCIDENTS.md)에서 각 단계에 무엇이 확정되는지 읽습니다. 문서·템플릿의 이름은 공식 필수 제출 파일명이 아닙니다.

## 8. 실제 결과를 자기 말로 설명하기

사전 연습에서는 **결론 → 선택 이유 → 실제 구현·관측 → 한계** 순서로 말해봅니다. 질문의 전제가 틀리면 그 전제를 바로잡습니다. 예를 들어 DB를 쓰지 않았는데 'DB를 선택한 이유'를 묻는다면 DB를 사용했다고 꾸미지 않습니다.

실제 AI 금지 단계에서는 AI 호출·답안 생성·미리 쓴 답 복사를 하지 않습니다. 설명 연습은 그 전에 끝냅니다. [사전 설명 연습](NO_AI_REHEARSAL.md)을 사용합니다.

## 준비 시간이 적을 때

- **20분:** 이 문서 → 현재 규칙·장비 → 질문 4개 → 구조와 근거를 직접 설명.
- **60분:** 핵심 10분 → [모의 A](../exercises/visitor-review/BRIEF.md)의 요구 정의·최소 구현/설계 25분 → 허용 근거와 한계 10분 → 직접 설명 15분.
- **충분한 사전 시간:** [모의 3종](MOCK_EXAMS.md) 중 취약한 하나를 실제로 수행하고 이후 6×5분 설명 연습.
- 체험 기회가 남았다면 [1회·15분 점검](TRIAL_15_MINUTES.md)을 실제 기기에서 참가자가 직접 합니다.

과거 Notion의 '오늘/내일'은 그 문서 작성일의 표현입니다. 10/30 하루 학습표를 10/31 시험 시간에 겹쳐 적용하지 않습니다. 학습량을 늘리느라 당일 준비와 시작 시각을 놓치지 않습니다.
