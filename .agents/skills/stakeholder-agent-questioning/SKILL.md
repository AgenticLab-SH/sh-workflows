# 구체 질문에만 답하는 담당자에게 묻기

공식 규칙·제공 환경·현재 호스트 정책이 이 Skill보다 우선한다. 허용된 담당자 채팅만 쓴다. 외부 AI 전송, Git Push, 캡처·GUI 자동화, Codex 업데이트, 감독 우회는 하지 않는다.
담당자는 사람일 수도 있고 업무·고객·운영 담당 역할을 맡은 담당자 에이전트일 수도 있다. 멘트는 Codex가 쓰지만 검토·전송·업무 판단은 참가자가 한다. Codex는 담당자 채팅에 직접 보내지 않는다.

용어: **질문**은 사실 하나를 묻는 문장이며 물음표가 하나다. **메시지**는 담당자 채팅에 한 번 보내는 전송 단위다. 메시지 하나에 질문 몇 개를 담을지는 4단계의 전송 단위 시험으로 정한다.

## 1. 질문 예산 판단
- 사람이거나 시간이 비싼 담당자: 기존 stakeholder-interview 방식으로 한 번에 2~3개만 묻는다.
- 무제한 여부는 공식 안내로 판단한다. 안내가 없으면 모호한 질문이 거절되고 질문 수 제한 안내도 없는 것을 관측했을 때 무제한으로 본다. 둘 다 아니면 제한 모드로 묻는다.
- 질문이 무제한이지만 구체 질문에만 답하는 담당자 에이전트: '애매하면 전부 묻기' 모드로 전환한다. 엣지 케이스, 해석이 갈리는 표현, 문서와 데이터의 차이는 모두 묻는다.
- 무제한 모드에도 범위가 있다. 결과·판정·테스트·화면을 바꾸지 않는 질문은 하지 않는다.
- P0·P1을 먼저 끝낸다(예: 과제 초반 20~30분 안). P3(표시 문구)는 기본 가정을 원장에 `assumed`로 기록하고 남는 시간에만 묻는다.
- 공식 규칙이 질문 횟수·시간을 제한하면 그 제한을 따른다.

## 2. 원천에서 결정 지점 추출
README·요구 문장·데이터 헤더·샘플 행을 읽고 결과가 달라질 수 있는 지점을 뽑는다.
- 모호한 용어(활성, 최근, 우선, 완료), 숫자와 단위(분/시간, 원/천원, 일/영업일)
- 경계(이상/초과, 이하/미만, 마감 당일 포함 여부), 포함/제외 대상
- 빈값·중복·이상치·형식이 다른 값, 동점과 우선순위, 규칙끼리의 충돌
- 문서 설명과 실제 데이터의 차이(문서에 없는 열, 문서와 다른 값 범위)
- 사용자 유형별 권한·화면 차이, 규모·응답 시간, 출력 형식·정렬, 평가·성공 기준
- 역할별 화면·출력에 꼭 있어야 할 구성 요소(예: 사서 화면의 연체 도서 목록·반납 처리·대출 연장 승인). 권한 질문만 하면 화면 구성을 놓친다.
- 데이터에서 보이는 결정 지점(빈 칸, 0·음수, 단위 혼재, 공백·대소문자만 다른 ID, 중복 ID, 같은 시각, 다른 파일에 없는 참조 값)은 `python3 .hackathon-kit/tools/question_candidates.py <파일.csv>... [--ref a.csv:열=b.csv:열]`로 후보 질문 초안을 원장 형식으로 뽑는다(키트 위치에 맞게 경로를 바꾼다). 출력은 초안이다. README로 이미 답이 나온 것을 지우고, 데이터에 드러나지 않는 목적·역할·화면·출력 형식 질문은 직접 더한다.

## 3. 범주 체크리스트로 후보 만들기
각 결정 지점마다 아래 범주를 대 보고 해당하는 것만 질문 후보로 만든다.
용어 · 데이터 필드 · 단위 · 경계값 · 포함/제외 · 빈값/중복/이상치 · 동점/우선순위 · 규칙 충돌 · 문서-데이터 차이 · 역할/권한 · 역할별 화면·출력 구성 요소 · 규모/성능 · 출력 형식/정렬 · 평가/성공 기준.
역할마다 '이 화면에 꼭 있어야 하는 것'과 '보이면 안 되는 것'을 따로 묻는다.

## 4. 정리와 우선순위
- README·기존 답변으로 이미 확정된 것과 서로 겹치는 후보를 지운다. 결과·판정·테스트·화면이 바뀌지 않는 후보도 지운다.
- P0: 설계·데이터 모델·핵심 판정을 바꾼다. P1: 처리 분기·예외·검증 사례·역할별 화면 구성을 바꾼다.
- P2: 정렬·출력 세부를 바꾼다. P3: 표시 문구·라벨만 바꾼다. P3는 기본 가정으로 기록하고 남는 시간에만 묻는다.
- P0를 먼저 보내고 P0·P1을 과제 초반(예: 20~30분 안)에 끝낸다. 답을 기다리는 동안 그 답에 영향받지 않는 구현은 계속 진행한다.
- 전송 단위 시험: 첫 메시지에 번호 붙인 질문 2개를 담아 보낸다. 둘 다 답하면 이후 메시지마다 질문 3~5개를 묶는다. 첫 질문에만 답하거나 거절하면 메시지당 질문 1개로 보낸다. 이때 답받지 못한 질문은 거절이 아니므로 status를 open으로 되돌리고 ask_count를 올리지 않으며, 같은 문장으로 다시 보내도 된다.
- 어느 쪽이든 멘트 작성은 Codex가 한 턴에 몰아서 한다. 반응을 확인하지 않고 한 개씩 따로 요청하지 않는다.

## 5. 멘트 작성 규칙
- 질문 하나 = 맥락 한 줄 + 질문 문장. 질문 하나에는 사실 하나와 물음표 하나만 둔다.
- 묶음 메시지에서도 질문마다 번호와 맥락 한 줄을 붙인다. 두 사실을 한 질문으로 합치지 않는다.
- 예/아니오, 수치, 제시한 선택지 중 하나로 답할 수 있게 쓴다.
- 담당자가 쓴 용어를 그대로 쓴다. 내 용어로 바꾸지 않는다.
- '어떻게 할까요', '적절히', '알아서', '등' 같은 열린 표현을 쓰지 않는다.
- 내 이해를 먼저 밝히는 확인형으로 쓴다(“…로 이해했습니다. …가 맞나요?”).
- 경계는 숫자로 묻는다(예: '정확히 10명일 때 포함인가요?').
- 질문 문장은 120자 안팎을 권장한다. 원장 lint의 `--max-length` 기본값 160은 질문 열의 상한이다.

## 6. 모호한 질문 → 구체 질문 (합성 예)
| 모호한 질문 | 구체 질문 |
| --- | --- |
| 대출 한도는 어떻게 처리할까요? | 1인 대출 한도가 5권일 때 정확히 5번째 책 대출은 허용인가요, 거절인가요? |
| 회의실 예약 시간 제한이 있나요? 등등 | 회의실 1회 예약은 최대 4시간으로 이해했습니다. 4시간 정각은 허용인가요? |
| 매장 재고가 이상하면 알아서 하면 될까요? | 재고 수량이 음수인 행은 오류로 표시하고 계산에서 빼도 되나요? |
| 도서 연체는 어떻게 계산하나요? | 반납 예정일 당일에 반납하면 연체 0일로 보면 되나요? |
| 고객 문의 우선순위를 적절히 정해 주세요. | 환불 문의와 배송 문의가 함께 있으면 환불 문의를 먼저 처리하나요? |
| 회원 화면은 다르게 해야 하나요? | 회원 화면에서는 다른 회원의 대출 내역을 숨겨야 하나요? |
| 사서 화면에는 뭐가 필요하죠? | 사서 화면에 회원별 반납 예정일이 꼭 보여야 하나요? |
| 결과 파일 형식은요? | 결과 CSV의 날짜는 YYYY-MM-DD 형식으로 내면 되나요? |

## 7. 복사용 멘트 블록 출력 형식
Codex는 보낼 질문을 번호와 함께 한 블록으로 출력한다. 참가자는 검토한 뒤 전송 단위 시험 결과대로 보낸다. 묶음이면 번호 블록을 메시지 하나로, 한 개씩이면 번호 하나를 메시지 하나로 복사한다.
```
메시지 1 · 질문 2개 (전송 단위 시험: 두 질문을 한 메시지로 전송)
[1] Q3 · P0
반납 예정일이 휴관일이면 다음 개관일까지 연체로 세지 않는다고 이해했습니다.
휴관일 다음 개관일에 반납하면 연체 0일인가요?
[2] Q4 · P1
사서 화면은 회원별 대출 목록을 보여 줄 계획입니다.
사서 화면에 반납 예정일이 지난 도서 목록이 꼭 있어야 하나요?
```
원장이 있으면 `python3 .hackathon-kit/tools/question_ledger.py next <원장.csv> --format text --limit 5`로 같은 번호 목록을 만든다. 키트 위치에 맞게 경로를 바꾼다.
`partial`·`unclear` 행은 '[다시 쓰기 필요: 쪼개기/선택지/샘플 행]'으로 표시되고 원문은 참고로만 나온다. 다음 순서로 다시 쓴다.
- 같은 행을 고칠 때: question(필요하면 context)을 바꾸고 status를 `open`으로 돌린다. ask_count는 그대로 둔다. 그러면 `next`가 고친 문장을 복사용으로 낸다. 보낼 때 status를 `sent`로 바꾸고 ask_count를 1 올린다.
- 새 행으로 쪼갤 때: 원래 행은 `answered`(답한 부분만 decision에 옮김) 또는 `dropped`로 닫는다. 닫지 않으면 P0·P1 원래 행이 미해결로 남아 멈춤 조건이 참이 되지 않는다.

## 8. 답변 원장과 재질문
- 원장 열: id, category, priority, context, question, status, answer, decision, test_case. 선택 열 ask_count는 이 항목을 보낸 횟수(첫 질문 포함)이며 비우거나 열이 없으면 0으로 본다. 보낼 때마다 1씩 올린다.
- status: open(작성) → sent(전송) → answered(확정) / partial(일부만 답함) / unclear(모호·거절) / assumed(가정 기록) / dropped(불필요).
- partial은 답한 부분을 decision에 옮기고, 남은 부분만 보완 질문으로 다시 쓴다(같은 행의 question을 고치거나 새 행으로 쪼갠다).
- 상태 전이: partial·unclear 행을 같은 행에서 다시 쓰면 status를 `open`으로 돌리고 ask_count는 유지한다. 보낼 때 `sent`로 바꾸고 ask_count를 1 올린다. 새 행으로 쪼갰다면 원래 행은 `answered`(답한 부분만 decision에) 또는 `dropped`로 닫는다.
- 답변 원문은 출처와 함께 남기고 공식 규정으로 승격하지 않는다. answer 칸 앞에 `[메시지 번호·시각]`을 붙인다(예: `[M3 10:42] 5권째까지 허용입니다.`).
- 답이 모호하거나 거절되면 같은 문장을 다시 보내지 않고 바꿔 묻는다: 질문 쪼개기, 선택지 2~3개 제시, 실제 샘플 행 하나를 들어 묻기, 내 가정을 제시하고 맞는지 묻기.
- 제안형 재질문("이 안으로 진행해도 되나요?")에 '제안해 주시면 검토하겠습니다'처럼 결론 없는 답이 오면, 선택지 2개 중 하나를 고르게 하는 선택형으로 바꿔 1회 더 묻는다(예: '반납 예정일이 휴관일이면 다음 개관일로 미루는 안과 그대로 두는 안 중 어느 쪽인가요?'). 이 선택형 재질문도 재질문 1회로 ask_count에 포함한다. 그래도 결론이 없으면 assumed로 기록하고 진행한다. 같은 제안을 되풀이해 보내지 않는다.
- 같은 항목은 재질문 최대 2회, 즉 전송 합계 3회(ask_count 3)까지다. 그래도 모호하면 가장 보수적인 가정을 assumed로 기록하고 결과·설명에 밝힌다. lint·next·summary는 status가 partial·unclear이면서 ask_count가 3 이상인 행만 `retry_limit`으로 본다. 세 번째 전송 후 답을 기다리는 `sent` 행과 보낼 차례인 `open` 행은 한도 판정에서 뺀다.

## 9. 구현·테스트 반영과 반복
- 확정 답은 decision과 test_case에 옮긴다. 가정과 미해결은 따로 적고 구현에서 바꾸기 쉬운 자리에 둔다.
- 새 답이 낳은 질문(새 경계, 새 예외)은 2단계로 돌아가 다시 후보로 만든다.
- 보내기 전 `python3 .hackathon-kit/tools/question_ledger.py lint <원장.csv>`로 복합 질문·열린 표현·중복·재질문 한도를 확인한다.

## 10. 멈춤 조건
P0·P1 질문이 모두 answered 또는 명시적 assumed가 되면 질문을 멈추고 구현에 집중한다.
`python3 .hackathon-kit/tools/question_ledger.py summary <원장.csv>`의 unresolved_p0_p1이 비어 있으면 된다. retry_limit에 나온 항목은 assumed로 기록한다. P2는 남은 시간에 맞춰 묻고, P3는 기본 가정으로 둔다.
