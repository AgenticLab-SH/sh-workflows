# 비용을 의식한 실행

사용 한도가 없다고 무료는 아니다. 토큰 양, 호출·턴 수, 재시도, 실행 시간이 평가 요소가 될 수 있다고 전제하고 일한다. 이 전제는 일반 가정이며 특정 대회의 배점이 아니다. 공식 규칙·제공 환경·호스트 정책이 항상 우선한다.

우선순위는 정확성과 필수 산출물이 먼저, 비용은 그다음이다. 비용을 줄이려고 필수 검증·입력 검증·사람 승인·정확성을 줄이지 않는다.

## 컨텍스트 규칙

- 과제 README와 지금 필요한 파일만 읽는다. 큰 파일·데이터는 앞부분 몇 줄이나 프로파일 요약(행 수·열·누락)으로 본다.
- Skill은 현재 단계에 필요한 1~3개만 로드한다. 키트 전체를 읽히지 않는다.
- 저장소 인벤토리는 한 번만 만들고 요약을 재사용한다. 같은 폴더를 반복 탐색하지 않는다.
- 작업 상태 요약 노트(결정, 확정 규칙, 남은 일)를 짧게 유지하고, 긴 대화나 파일을 다시 읽는 대신 이 노트를 붙인다.
- 큰 출력과 전체 파일 재생성을 피한다. 바뀌는 부분만 수정하게 한다.
- 합계·비율·건수 같은 계산은 스크립트로 한다. 모델이 데이터를 눈으로 보고 계산하게 하지 않는다.

## 구현·디버깅 규칙

- 테스트는 바꾼 부분의 좁은 테스트를 먼저, 전체 테스트는 체크포인트에서 실행한다. 정책이 금지한 검사는 NOT_RUN으로 남긴다.
- 같은 실패가 2회 반복되면 같은 지시를 다시 보내지 말고 접근을 바꾼다(원인 가설, 범위 축소, 입력 최소화).
- 작은 수정 여러 개는 묶어서 한 번에 위임한다.
- 위임 프롬프트에는 대상 파일, 완료 기준, 멈춤 조건을 적는다. "전부 개선해" 같은 넓은 지시를 쓰지 않는다.
- 하위 에이전트·병렬 실행은 제공·허용되고 효과가 확실할 때만 쓴다. 같은 파일의 작성자는 한 명이다.
- 업무 담당자 에이전트에 보내는 질문도 호출 비용이다. 결과를 바꾸는 P0 질문부터 고르고, 멘트는 한 턴에 묶어 작성한다. 전송 단위는 담당자가 받는 방식에 맞춘다(묶음에 모두 답하면 묶어서, 첫 질문에만 답하면 하나씩).

## 모델·노력 수준

- 제공 환경의 기본·권장 모델을 유지한다.
- 높은 추론은 문제 정식화, 알고리즘 설계, 어려운 디버깅에만 쓴다. 기계적 수정·서식 정리는 낮게 둔다.
- 변경은 제공 환경이 허용한 메뉴(예: `/model`)가 있을 때만 한다. Codex 업데이트나 설정 파일 변경은 하지 않는다.

## 세션 관리

컨텍스트가 커지면 상태 요약 노트를 먼저 갱신한다. 그다음 `/compact`가 제공되면 사용하거나, `/new` 등으로 새 세션을 열고 인계 요약만 붙인다. 이런 명령이 없으면 요약 노트만 유지한다.

## 비용 점검 단계

1. 기능 1개를 끝낼 때마다 또는 30~45분마다 점검한다.
2. `/status` 같은 사용량 표시가 제공되면 값을 확인한다. 없으면 대략의 턴 수만 센다.
3. COST_LOG에 한 줄 기록한다: 시각, 작업 단위, 턴 수, 읽은 주요 파일, 큰 출력 여부, 재시도, 표시값, 조치.
4. 낭비 신호를 보면 바로 교정한다: 같은 파일 재독, 긴 출력, 반복 실패, 넓은 지시.
5. 사용량을 숨기거나 측정값을 꾸미지 않는다. 기록은 실제 관측만 적는다.

## 설명할 때

"비용을 줄이려고 한 일 3가지"를 COST_LOG의 실제 기록으로 말한다. 예: 데이터는 요약 스크립트로만 봤다, 질문을 한 번에 묶었다, 2회 실패 후 범위를 좁혀 재위임했다. 하지 않은 일을 했다고 말하지 않는다.
